# Connectors

Connectors let the AI use services you already have: "what's due on Canvas this week", "summarize my unread email", "draft a reply to my professor", "add a task to Todoist", "comment on that pull request", "put these notes in a Notion page", "find my lab notes in Drive", "upload this PDF to my Reports folder", "add these rows to my grades sheet". You connect each one in **Settings → Apps and connections**. Nothing is connected until you press **Connect**, and an unconnected service adds nothing to what the AI is told.

## The list (Settings → Apps and connections)

Connectors and the new tab page's widgets are one list now: each service has one page with Connect, **Show on new tab page** and **Let the AI use it** (turning that off keeps you signed in). See docs/settings.md, Apps and connections. What follows still describes what each connector does.

Cards are grouped as Mail and calendar, School, Files and docs, Work and Tasks, with **Custom MCP servers** under them. Each card shows what it is for, its state (**Not connected**, **Connected · account**, **Needs sign-in**, **Token refused**) and one button. **What it can do** on a card lists exactly what the AI can read and do with it. Connect shows the same list before you confirm.

## How the AI uses them

The AI gets one tool, `connector(app, action, args)`, whose description lists only the connected apps and their actions, one line each. Asking for `help` on an app explains its actions. This keeps the prompt small however many services you connect.

- **Reads** run straight away, and the step in the chat reads "Using Canvas · Upcoming assignments". What comes back is untrusted data, like a web page: once the AI has read it, the chat counts as having read page content, so a new site or a change asks first.
- **Writes** always ask, with the exact change on the card, and need a real click on **Allow** (Enter doesn't allow, and there is no "Always allow"). Auto-allow, **Bypass permissions** (in the background too), "Agents in their own window don't ask" never answer them, and hands-off mode blocks them. The one exception: a Gmail send you allowed by typing in the chat skips the card (10 second Undo); see [Gmail sending](#gmail-sending). **Background tasks and routines** are offered the reads only, and a write they ask for anyway is refused. See [Writes](#writes).
- The sidebar and the full-page chat get the tool, whether the chat runs on an API model or on a command-line engine Lumen starts itself (Claude Code, Codex, Grok Build, Antigravity). Each such run connects to Lumen's MCP server with a random per-run tag that Lumen writes only into that run's own temporary config; the tool is listed and callable only for a session carrying a live tag, with the same rules as above (reads run, writes need a real click, results are untrusted). A command-line process that was already running when you connected a service lists its tools when it starts, so it sees the new service in the next chat.
- **Outside agents over MCP never get it** (a Claude Code you started in a terminal, an editor, any other app): it isn't in the tool list they get, and a call to it, or one with a forged tag, is refused with `Unknown tool`, so a program that can drive your browser can't read your mail or school account. Background tasks don't get it either. Letting a specific outside agent use a specific service would be its own opt-in, which doesn't exist yet.

## Why GitHub, Notion and Todoist are built in, and Custom MCP servers

Each of these services has an official, maintained remote MCP server, and Lumen's MCP client can connect to it (including OAuth sign-in). They are still built-in connectors because the official servers describe far more tools than the one `connector` tool does, and those definitions are sent on every message:

| Service | Official server | Its tool definitions | The built-in connector |
|---|---|---|---|
| GitHub | `https://api.githubcopilot.com/mcp/` ([docs](https://github.com/github/github-mcp-server)) | 24 tools, about 32,000 characters, even limited to the `context`, `issues` and `pull_requests` toolsets (about 51,000 with `repos`, about 158,000 unscoped) | 5 actions, about 136 characters |
| Notion | `https://mcp.notion.com/mcp` ([docs](https://developers.notion.com/guides/mcp/mcp-supported-tools)) | 64 tools, about 45,000 characters by the vendor page's size (an estimate) | 4 actions, about 102 characters |
| Todoist | `https://ai.todoist.net/mcp` ([Doist/todoist-mcp](https://github.com/Doist/todoist-mcp)) | about 45 tools, no published schema to measure (counted as over budget) | 3 actions, about 94 characters |

The rule: a built-in connector is replaced by the official server only when that server's tool definitions are small (under about 5,000 characters as Lumen wraps them) or it does clearly more for the same cost. Canvas has no official server. Google's (Gmail, Calendar, Drive, Sheets) need a Google Cloud project and a developer preview, and Slack's needs a Marketplace or internal Slack app, so those aren't an option either; Slack and Spotify have no connector at all.

**Custom MCP servers**, under the cards on the same page, add any MCP server you want, including these official ones for their full tool set (GitHub: the address with an `Authorization: Bearer <token>` header; Notion and Todoist: the address with **Sign in with the service**). Each card says so. What an MCP server's tools cost per message is on you: it grows with the tools it lists.

- **OAuth** follows the MCP authorization spec: Lumen finds the server's sign-in details from its 401 (RFC 9728, RFC 8414), registers itself once (dynamic client registration, as a native app with a `127.0.0.1` redirect and no secret), opens the service's sign-in page in **your own browser** with PKCE (S256) and the `resource` parameter, and finishes when the browser comes back to a one-shot listener on this computer. Tokens are sealed with the system keyring inside the server's entry in `mcp-servers.json`; the access token lives in memory, a refresh is one request at a time and keeps a rotated refresh token at once, and a revoked grant turns the server to **Needs sign-in**. Sign-in addresses must be https (http only for a server on this computer). A server with no automatic registration (GitHub's, Slack's) needs a token header instead.
- A server's tools ask before every call, with what they would send, unless you tick **Always allow** for that tool (and after the chat has read a page, they ask again). Outside agents never get them. A connector card can be one that adds a service's official server in one click (a `kind: 'mcp'` preset; none ships today): there a tool the server itself marks read only (`readOnlyHint: true`) runs without a card, nothing else does, and a custom server never gets that pass.
- The Custom MCP servers list is the old "Tools from MCP servers" page, moved here (its link still opens this page).

## Google Drive and Sheets

Drive and Sheets sign in with Google in **your own browser**: **Connect** opens Google's consent page, you approve, and Lumen finishes in the app. One Google sign-in serves both cards: the first connector asks for its own permissions, the second asks Google to add its own to what you already gave (and doesn't open the browser at all if the sign-in already covers it). Lumen never sees your Google password.

- **Drive asks for** `drive` (full access to your Drive files), in place of the older `drive.readonly` + `drive.file`. With it the AI can read, and on a card change, ANY file you own or can edit, not just files Lumen made. `drive` is a Google "restricted" scope, like `gmail.readonly`, so it brings the same "Google hasn't verified this app" warning on an unverified client. The OAuth consent screen of the client you build with (`LUMEN_GOOGLE_CLIENT_ID`) must list `https://www.googleapis.com/auth/drive` (replacing `drive.readonly` and `drive.file`), and the verification request should name it.
- **If you connected Drive before.** Your sign-in only has the older permissions. Reading keeps working, but the Drive card shows **Reconnect to let the AI change all your files** (status Needs sign-in) and any edit (replace, rename, move, copy, trash) is refused before a card with "press Connect on Google Drive"; Google's own "insufficient permission" answer says the same. Press **Connect** on the Drive card: Google's page asks only for the one new permission on top of what you already gave (incremental consent, same account), and the card is Connected again.
- **Sheets asks for** `spreadsheets` (read and edit cells). Nothing is edited without a card.
- **What the AI can read.** Names, dates and sizes of files, and the text of a Google Doc, Slides deck, Sheet (first tab as CSV) or a text file, at most 8,000 characters of it at a time. PDFs, pictures and other binary files are listed with their link only.
- **Uploading a file from this computer.** The AI never names a file on its own: it passes `file` (the ref of a file you attached to the chat, the same store `upload_file` uses) or, only when **Settings → AI → Let the AI use files on this computer** is on, a `path`. A path goes through the same checks as every other use of your files: nothing in Lumen's own profile, `~/.ssh`, `~/.aws`, `~/.gnupg` and the other credentials folders, or `.env`, key and token files. **One file per call, and each call is its own card** naming the file, its size, where it goes and that its contents go to Google, with the name in Drive in a box you can change. Bypass permissions, Auto-allow and "Always" never answer it. If the file changes between your click and the upload, it is not uploaded. A file up to 5 MB goes in one multipart request; a bigger one (up to 100 MB) through a resumable upload session. The upload is sent once and never repeated: if the connection fails after the bytes went, the AI is told "may have been made; check Drive before trying again".
- **Replacing files you already have.** `update` uses the same local-file rules as an upload (a chat attachment by `file`, or a `path` only with **Let the AI use files on this computer** on; never Lumen's profile or a credentials folder), for every file in the call. The AI never picks the Drive file for a name by itself: with `folder_id` the card shows which Drive file each local file would replace, found by **exactly the same name** in that folder (case and extension included), and only those pairs are sent. A name with no match or two matches is skipped and listed on the card, not guessed; if nothing matches there is no card, only the reasons. Two local files with the same name in one call are refused. Up to 25 files and 500 MB in all per call; a bigger set takes several calls and cards. Each file is sent once as a media update (up to 5 MB in one multipart request, larger through a resumable session) and never repeated; if one fails (Google refuses it, or it changed after your click) the others still go and the answer lists each result, but an ended sign-in or a rate limit stops the rest ("Not tried"). A file that failed after its bytes went may have been replaced: the AI is told to check Drive. A Google Doc, Sheet or Slides file can't be replaced by a file (the card says so; the `document` tool edits a Google Doc in its page). Drive keeps the earlier content as a version of the file (non-Google files: for a limited time, about 30 days).
- **Rename, move, copy, trash.** Each is one file or folder per call and one card naming it (looked up with a read; the id if that fails), what changes and where it goes. Rename and copy show the name in a box you can change. Move takes the file out of all its current folders and into the one named. Trash only sets "trashed" on the file; there is no delete action and Lumen never sends a delete request, so nothing is lost for good (restore it from Drive's Trash). None of these can be run from a background task or routine, by an outside MCP agent, or without your click on **Allow**.
- **Rows are text.** **Add rows** writes the cells as plain text (`valueInputOption=RAW`), so a web page or email can't get a formula such as `=IMAGE(...)` or `=IMPORTDATA(...)` into your sheet through the AI. At most 200 rows of 50 cells, 1,000 characters a cell, per call.
- **Disconnect.** Each card disconnects on its own. The shared sign-in is kept while one of them is connected, and given back to Google (revoked) when the last one goes. Disconnecting one of two therefore doesn't narrow what the sign-in can do until both are gone.
- **When it can't connect.** Lumen's Google client comes with the release build. A build without one says so and points to the Gmail widget's **Advanced** fields: a Google Cloud client of type Desktop app that you typed there is used for Drive and Sheets too, if you turn on the Google Drive API and the Google Sheets API in that project. Google can show "hasn't verified this app" until Lumen's client is verified for these scopes; **Advanced → Go to Lumen** gets past it.
- **Not included.** Google Calendar events are added by the Google Calendar card below, not through Drive. Deleting files for good, changing who a file is shared with beyond "anyone with the link can view", and editing the text inside a Google Doc through Drive are not offered.

## More Google connectors

Google Docs, Google Calendar, Google Tasks and Google Contacts use the **same Google sign-in** as Drive and Sheets (kind `google`): **Connect** opens Google's consent page in your browser, asks only for the new connector's permission added to what you already gave (incremental), and opens nothing at all when the sign-in already covers it. Each card disconnects on its own; the shared sign-in is given back to Google when the last Google connector goes.

| Connector | Permission asked | Why |
|---|---|---|
| Google Docs | `https://www.googleapis.com/auth/documents` | Read a document and add text to it (Google has no narrower permission that reads your existing documents and edits them). Nothing is changed without a card. |
| Google Calendar | `https://www.googleapis.com/auth/calendar.events` | See, add and change events on your calendars. Lumen only uses your main calendar, never adds guests, sends `sendUpdates=none`, and has no delete. |
| Google Tasks | `https://www.googleapis.com/auth/tasks` | See, add and tick off tasks. No delete. |
| Google Contacts | `https://www.googleapis.com/auth/contacts.readonly` | Read-only: find a contact. |

- **For whoever owns the Google Cloud project Lumen signs in with** (or the user's own client under Gmail's **Advanced**): the consent screen must list these four scopes, and the **Google Docs API**, **Google Calendar API**, **Google Tasks API** and **People API** must be enabled in the project. A project without one of them gives a message that says so ("the API isn't turned on…"), not a failure. These are sensitive (not restricted) scopes.
- **Google Calendar vs Calendar (secret address).** The secret-address card (id `gcal`) stays as it was: it only reads, needs no Google sign-in, and keeps working for anyone who connected it. The **Google Calendar** card is a separate connector (id `calendar`) that can also add and change events. Connect whichever you prefer; connecting both just gives the AI two sources.
- **Dates.** A start or end is `2026-11-03T14:30` (a local time in this computer's time zone) or `2026-11-03` (all day). For an all-day event the end is the **last** day (the same day: a one-day event). A move keeps the event's length. A date that doesn't exist, an end before the start, or a date mixed with a time is refused before any card.
- **Docs text is plain.** Text goes in as plain text at the end of the document (or as the first text of a new one); formatting, links and scripts can't be planted through the AI. At most 20,000 characters at a time.
- A write whose request fails in transit or gets a server error says "may have been made; check …" and the AI is told to look before trying again; Lumen never repeats a write by itself.

## Microsoft: Outlook, OneDrive and Outlook Calendar

The three Microsoft cards share **one Microsoft sign-in** in your own browser (kind `microsoft`), built like Google's: **Connect** opens Microsoft's consent page, you approve (a school or work account such as Northeastern's, or an outlook.com account), and Lumen finishes in the app. Lumen uses Authorization Code with PKCE and a `http://localhost` redirect to a one-shot listener on your computer, as a **public client** (no secret anywhere). The refresh token is kept encrypted in `connectors.json` under `microsoft`; Microsoft rotates it on each refresh and Lumen keeps the newest. Every request goes to `graph.microsoft.com` over https.

| Connector | Graph permission (delegated) | What it is for |
|---|---|---|
| Outlook | `Mail.ReadWrite` | Read mail, and put a draft in Drafts. Microsoft has no narrower permission for drafts; Lumen never sends, moves or deletes mail. |
| OneDrive | `Files.Read` | Read only. |
| Outlook Calendar | `Calendars.ReadWrite` | See, add and change events. No attendees, no delete. |
| (all) | `User.Read`, `openid`, `email`, `profile`, `offline_access` | Who you are (shown on the card) and the refresh token. |

- **OneDrive reads Office files.** A `.docx`, `.xlsx` or `.pptx` (up to 15 MB) is downloaded from the short-lived address Graph gives and read by Lumen's own readers (the same ones as the file previews: no macros run, no formulas calculated, nothing fetched); plain text files are read as text; PDFs, pictures and old `.doc`/`.xls` files give their details only. The download address must be on a Microsoft file host (`sharepoint.com`, `1drv.com`, `onedrive.live.com`, `microsoftpersonalcontent.com` and the like), is fetched with no sign-in header and no redirect is followed.
- **A school account may need its administrator.** Mail, Files and Calendar permissions are normally yours to give, but a university can require administrator approval for new apps. Then Microsoft says so on its page, and Lumen says to connect again once it is allowed.
- **The sign-in app.** A release build may include Lumen's own Microsoft Entra app (its Application (client) ID from the `LUMEN_MS_CLIENT_ID` build secret, a GUID, not a secret). A build without one asks on each Microsoft card for **Advanced: your own app's client ID**: register an app in the Microsoft Entra admin center (accounts in any organizational directory and personal Microsoft accounts; the **Mobile and desktop applications** platform with the redirect address `http://localhost`; delegated permissions `Mail.ReadWrite`, `Files.Read`, `Calendars.ReadWrite`; public client flows allowed) and paste its client ID. An ID typed there is used instead of the built-in one, and later Microsoft connectors keep using it.
- **Disconnect** forgets the sign-in on this computer when the last Microsoft card goes. Microsoft has no revoke call for a public client, so to take the permission back at Microsoft too, remove Lumen in your Microsoft account's app permissions (account.microsoft.com/privacy/app-access, or myapps.microsoft.com for a school account).
- Times are shown and sent in this computer's time zone (`Prefer: outlook.timezone`). Dates are written as for Google Calendar above.

## Zotero

Zotero connects with an **API key** you make at zotero.org/settings/keys/new (tick **Allow library access**; read only is enough). It is sent as `Authorization: Bearer` to `api.zotero.org` only. The AI can search your personal library, list collections and their items, and read one item's title, authors, year, publication, DOI, link and abstract. It never reads notes or attachments and can't change anything.

## One-click MCP servers

These five cards add the service's **own official MCP server** under **Custom MCP servers** and sign you in with OAuth on its page (kind `mcp`, no token to paste). Disconnecting removes the server and its sign-in. Unlike the built-in connectors, a connected MCP server's tool definitions are sent with every message, so each card says to connect it only when you use it. A tool the server itself marks read-only runs without a card (as the reads of the old GitHub, Notion and Todoist connectors did, and the chat then counts as having read untrusted content); every other call asks first, with what it would send, unless you tick **Always allow** for that tool.

| Card | Server | Checked 2026-10-25 |
|---|---|---|
| Linear | `https://mcp.linear.app/mcp` ([docs](https://linear.app/docs/mcp)) | Answers 401 with sign-in details; registers Lumen's `127.0.0.1` redirect; PKCE S256. |
| Atlassian (Jira and Confluence) | `https://mcp.atlassian.com/v2/mcp` ([docs](https://developer.atlassian.com/cloud/rovo-mcp/guides/getting-started/)) | Same. A site administrator can limit which apps may sign in. |
| Sentry | `https://mcp.sentry.dev/mcp` | Same. |
| Canva | `https://mcp.canva.com/mcp` | Same. |
| Hugging Face | `https://huggingface.co/mcp` | Same; works without sign-in for public search too. |

Only servers whose sign-in publishes dynamic client registration and accepted a registration for Lumen's redirect when checked are listed. Not offered, because they need an app registered with the service first or an API key: Asana (its authorization server "does not support dynamic client registration"), Slack, Figma and Vercel (only reviewed clients), Dropbox and Box (trusted clients only), Zapier (an API key per user), and Microsoft and Google (no hosted server with open registration: Outlook, OneDrive and Google Docs, Calendar and Tasks use the built-in connectors above).

## Gmail drafts
The AI can put an email in your Gmail **Drafts**: a new one, or a reply in the conversation of a message it found. A draft is not sent. You open it in Gmail, change it if you like, and send it yourself (or turn on [Allow sending](#gmail-sending)).

To turn it on:

1. Connect Gmail with the full Google sign-in (**Connect** on the Gmail card in **Settings → Apps and connections**, or **Sign in with Google** on the Gmail widget: both use the same sign-in).
2. Press **Allow drafts** on the Gmail card. Your browser opens Google's page, which asks you to let Lumen **manage drafts and send emails** for that account (Google has one permission for both, `gmail.compose`). Make sure that box is ticked and press **Continue**.
3. The card then says **Drafts allowed**. Ask the AI something like "draft a reply to the last email from my professor".

- Lumen asks Google for this only when you press **Allow drafts**, never at the first sign-in. The sign-in adds it to the read access you already gave (incremental authorization), and Lumen keeps the list of permissions Google says the sign-in has. Before every draft it checks that list.
- Google's permission covers sending too. A draft request itself only creates a draft (`POST /users/me/drafts`), and anything aimed at a send address is refused before it leaves the computer. Sending is a separate switch, below.
- Each draft shows a card with **To**, **Cc**, **Subject** and the text in boxes you can change, and the line "This only makes a draft. Nothing is sent." For a reply, the card names the conversation. **Allow** needs a real click, as for every write. The chat then shows "Gmail · Draft made" with **Open**, which opens the draft in Gmail in a new tab.
- **Allow drafts** is for the account already signed in. If you pick another account on Google's page, Lumen keeps the sign-in it had, gives the new one back to Google and says "Choose <your address> to allow drafts for it."
- The draft request is sent once and never repeated by itself. If the connection fails after it was sent (a timeout, a dropped connection), or Google answers with a server error or something Lumen can't read, Lumen can't know whether Google made the draft, so the AI is told "The draft may have been made; check Drafts before trying again", with a link to your Drafts. **Open** and that link open Gmail for the signed-in account (`?authuser=` your address), even with several Google accounts signed in.
- Without **Allow drafts**, or if you took the permission back in your Google Account, the AI is told "Allow drafts first", with no card; the card in Settings offers the button again. If Google ended the sign-in, the card says **Needs sign-in**: connect again.
- A draft is plain text. Addresses are checked, a subject with characters outside ASCII is encoded the standard way, and a line break in To, Cc or Subject is refused.
- Signing in to Gmail again without **Allow drafts** (for example from the widget, or with another account) gives a read-only sign-in again; press **Allow drafts** once more. To take the permission away, disconnect the Google sign-in (see below) or remove Lumen at [myaccount.google.com/permissions](https://myaccount.google.com/permissions).

## Gmail sending

**Allow sending** is a second switch on the Gmail card, under **Allow drafts**. It is off by default and appears only after drafts are allowed. It asks Google for nothing new: the `gmail.compose` permission you gave for drafts also covers sending. While it is off, the AI is told "Sending is off" and can still make drafts.

- **The card.** Each send shows From, To, Cc, Bcc, Subject, the whole text and the attachments, with **Send** and **Cancel**. Nothing goes until you click **Send**. There is no "Always", and Auto-allow and **Bypass permissions** never answer it. A recipient the AI did not get from you is flagged.
- **Typed permission.** If you type in a chat that the AI may send ("email jane@x.org that I'll be late and send it", or "you can send emails without asking"), that chat sends without the card, only to addresses you typed (or to whoever wrote the message you asked it to reply to). Each such send waits 10 seconds with an **Undo**, and a Stop button takes the permission back. Words from a page, an email or a tool never count, and a new chat asks again.
- **Limits.** At most 10 emails an hour. Background tasks and routines never send.
- **What goes where.** The email goes to Google's Gmail API (`POST /users/me/messages/send`) from your account. Nothing goes to Lumen or anyone else.
- **The send log.** Lumen keeps the last 200 sends in `gmail-send-log.json` in the profile folder: the time, the recipient addresses, the subject and whether it went by card or by typed permission. The file is encrypted with your system's keychain, like the tokens (a log from an older version is encrypted the next time Lumen starts), and is written to a temporary file that is then renamed, so a crash can't leave half a file. It also enforces the hourly limit, and it fails closed: if the file can't be read or opened (for example after a change of keychain), Lumen keeps it, sets a copy aside as `gmail-send-log.json.corrupt-<time>`, and refuses to send rather than starting the count again from zero. **Sent by the AI** on the Gmail card lists it. Turning off **Allow sending** or disconnecting does not clear it; delete the file (and `gmail-send-log.json.bak`, the previous copy) to remove it.
- **Turn it off.** Press **Turn off sending** on the Gmail card.

## Where your secrets go

- A token or secret address is saved encrypted with your operating system's own encryption (the same way saved passwords are), in `connectors.json` in the profile folder, next to the account name shown on the card. The settings page never gets a token back, only whether one is saved.
- Requests go only to the service itself (for Canvas, your school's address), over https, and redirects are not followed. Canvas uses the signed-in session you already have in Lumen; the others send their token in a header. Nothing goes to Lumen or anyone else.
- What a service returns goes into your chat, so it is also sent to the AI you are using (Anthropic, OpenAI, Google, xAI or whichever you picked), like the text of a page. Connect says so.
- Answers are kept in memory for 30 seconds so asking twice is one request. They are not written to disk. The one thing a connector keeps on disk besides the token is the [Gmail send log](#gmail-sending), if you use sending.
- **Disconnect** deletes the saved token and the card's entry and drops cached answers at once. For Gmail, the Google sign-in made by the Gmail widget stays (it is the widget's); one made from the connector is revoked.
- The Gmail widget's **Sign in with Google** and the Gmail connector share one Google sign-in (one token, kept encrypted). **Allow drafts** adds its permission to that shared sign-in, so it lasts until the sign-in is revoked: disconnecting a connector-made sign-in, or **Disconnect** on the Gmail widget in Settings, gives the token back to Google.
- **Microsoft** (Outlook, OneDrive, Outlook Calendar): requests go to `graph.microsoft.com` (and, for a OneDrive file, the Microsoft file host Graph names, with no sign-in header) and the sign-in to `login.microsoftonline.com`. The sign-in opens in your own browser; Lumen never sees your password. Mail text, event details and file text go into your chat and so to the AI you picked, like any connector. See [Microsoft](#microsoft-outlook-onedrive-and-outlook-calendar).
- **Zotero** sends its API key to `api.zotero.org` only. The **MCP presets** send what their server's tools are given to that server, after you allow each call.

## For developers

- `src/features/connectors/registry.js` declares each connector (id, name, icon, category, kind, fields, what it reads and does, its actions with tight argument schemas) and builds the single tool and its input check. `service.js` holds what is connected, the sealed secrets, the request helper and the dispatcher. `providers/` has one small file per service, loaded only when one is used. None of it loads at startup (`test/e2e/perf-budget.js`); `main.js` answers "is anything connected" from the small file until something needs the service.
- Tests: `test/units/connectors-units.js` (registry, tool size, input checks and the service against stand-in servers), `test/units/connector-writes-units.js` (each write's request with an injected fetch, the card's edits, the read-only messages, and the agent's gate: no bypass, background refusal), `test/units/mcp-oauth-units.js` (OAuth against a stand-in server), `test/units/mcp-readonly-units.js` (read-only presets), `test/units/gmail-drafts-units.js` (the message Lumen builds, the Allow drafts sign-in and scope check, the drafts-only request, and the gate for drafts) and `test/e2e/connectors.js` (the settings page, the AI with a fake model, approvals, MCP and disconnect in a real window). Stand-ins for Canvas, GitHub, Todoist, Notion and a calendar are in `test/fixtures/fake-connectors.js`; in test mode only, `global.__connectorEndpoints` points a connector at 127.0.0.1.
- Names that go into a request path (a GitHub owner/repo) are checked for `.` and `..` segments and any of `/ \ ? #`; ids in queries are plain words.
- Drive and Sheets: `kind: 'google'` with `google.scopes` in `registry.js`; `google-auth.js` is the one Google sign-in (the consent page in the browser, the loopback redirect, incremental scopes, refresh, revoke), sealed into `connectors.json` under `google`; `service.js` `connectGoogle` and the access token the shared `ctx.http` adds (one retry after a 401); `providers/drive.js`, `providers/sheets.js` and `providers/_google.js` (answers and errors). `agent.js` `connectorUploadFile` resolves the one file of an upload (a chat attachment by ref, or a path through `device-access.js`) before the card, and `runConnector` hands exactly that file to the provider, which checks it has not changed. An update does the same for each file (`connectorUpdateFiles`), the provider looks up which Drive file each would replace for the card (`cardNames`/`planUpdate`), and `connectorUpdatePairs` hands `runConnector` only the pairs the card showed. A connector's `ctx.hasScopes()` says whether the sign-in covers the scopes it asks for now; Drive's edits check it (`beforeCard`), and the card shows a Reconnect line when it doesn't. Tests: `test/units/google-connectors-units.js` (a stand-in Google: sign-in, refresh, revoke, every request, multipart and resumable upload, the errors, the agent's card and refusals).
- Google Docs, Calendar, Tasks and Contacts: more `kind: 'google'` entries (`providers/docs.js`, `calendar.js`, `gtasks.js`, `contacts.js`) on the same `google-auth.js` sign-in. The calendars share `dates.js` (checking and shifting the dates the AI gives). `providers/_google.js` and `_graph.js` read each service's errors.
- Outlook, OneDrive and Outlook Calendar: `kind: 'microsoft'` with `microsoft.scopes` (`providers/outlook.js`, `onedrive.js`, `mscal.js`). `microsoft-auth.js` is the shared sign-in (same shape as `google-auth.js`: a public client, PKCE, a `localhost` redirect via `oauth.js` `redirectHost`, incremental scopes asked as a union, rotated refresh tokens); `features/microsoft-client.js` reads the built-in client ID (`LUMEN_MS_CLIENT_ID`, written into `microsoft-client.json` by `scripts/build/build.js` and passed by `release.yml`). `ctx.download(url)` fetches a OneDrive file from a Microsoft file host only. The card's optional `clientId` field is the "your own app" path.
- One-click MCP servers: `MCP_PRESETS` in `registry.js` (kind `mcp`, `mcp.auth: 'oauth'`); add one only after checking its server answers 401 with sign-in details and registers a `127.0.0.1` redirect.
- Tests: `test/units/more-connectors-units.js` (every provider with a stand-in fetch, the two sign-ins, the cards' text, the agent's gate for the new writes, the presets).
- To add a connector: declare it in `registry.js`, add `providers/<id>.js` exporting `verify(ctx)` and `actions`, and add a fake to the fixtures.
- A write action has `write: true` and `edit: [...]` (the text arguments the card lets the user change). Its provider returns `{ text, link, done }` and exports `describeWrite(action, args, names)` (everything sent) and `describeWhere` (the fixed part); an optional `cardNames(ctx, action, args)` looks up names for the card. `agent.js` `allowConnector` asks with `noBypass` and `noAlways`, applies the edits (`registry.applyEdits`), and refuses writes in background runs; `service.call(input, { readOnly })` refuses them too.
- Gmail drafts: `features/gmail-drafts.js` builds the message (RFC 2047 headers, header line breaks refused, base64url) and `composePath()` allows `POST /users/me/drafts` only and refuses any path with a `send` part; `widgets.js` `gmailCompose` is the only code that posts to Gmail, and `gmailAllowDrafts` the incremental sign-in (`GV.signInParams({ compose: true })`: `gmail.readonly gmail.compose`, `include_granted_scopes=true`, `login_hint`). The token answer's `scope` is stored with the sign-in (`oauth.js` `encodeCreds`) and refreshed with it. The provider's `beforeCard` refuses a draft without compose before any card is shown.
- Google OAuth verification: `gmail.compose` is a restricted Gmail scope, like `gmail.readonly`, so adding it doesn't change the kind of review Google asks for, nor the "Google hasn't verified this app" warning users of an unverified client see. The OAuth consent screen of the client you build with (`LUMEN_GOOGLE_CLIENT_ID`) must list `gmail.compose` next to `gmail.readonly`, and the verification request should name both.
